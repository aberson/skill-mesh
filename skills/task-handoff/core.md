# NOTE: This is the canonical provider-independent contract. Every provider wrapper must load it in full.

# task-handoff core

## Intent continuity (drift-ranger)

Follow the intent continuity contract at `<repo>/_shared/intent-continuity.md`.
On every checkpoint and resume, preserve the private intent-record locator, original user journey, actual entry point, current capability, next gap, delivery stage and no-progress streak. Use the existing private WIP section; do not change the session parser schema. Read the record before following Next Action and reconcile any mismatch. Do not count a handoff as a work unit or reset the streak. Never carry private intent into committed MEMORY.md or public handoff text.

## Purpose and complete operating contract

Checkpoint library for task-state writes and reads. Its callers are orchestrating skills that
need a durable checkpoint or an in-window resume: `build-phase` and `build-step`
(`--loop [--no-commit]`), `plan-expedite` (`--next-task`), `session-wrap` (`--loop [--no-commit]`;
it is also the target of `--end`) and `user-draft` (`--loop`; it emits `--resume`). `user-pm`
emits `--resume`, `user-wrap` mirrors its orientation shape, and `user-project`'s pin must survive
every write. Operators wanting a session transition should use `/session-wrap`.

**Accepted invocations (closed list):** bare `/task-handoff` (= `--resume`), `--loop`,
`--loop --no-commit`, `--next-task [label]`, `--resume`, `--end`. Any other flag or combination
(for example `--next-task --no-commit`, `--loop --next-task`, `--next-action-file`) writes
nothing — no session file, rollup, memory update, commit or push — and returns
`Checkpoint not written: unsupported invocation <arguments>.`

**task-state contract:** the per-session file model (each session writes only
`sessions/<session-id>.md`; `current.md` is a DERIVED rollup regenerated by
`.claude/hooks/lib/task-state-derive.ps1`), file format, field split, path resolution,
staleness, session identity, and lifecycle are owned by
`.claude/references/task-state-schema.md` — follow it for every read and write, except in the
two scoped places below. Safety-critical minimum: resolve the Git root via
`git rev-parse --show-toplevel`, never cwd-relative.

**Scoped departures from the schema doc (these points only; every other schema rule governs):**
1. *Path survival.* In a linked worktree `--show-toplevel` names that worktree, not the main
   checkout, so a checkpoint written there is deleted with the worktree. Never redirect state
   into another live worktree or the common Git directory. This corrects the schema's
   § Path resolution sentence for this survival claim only.
2. *Fallback execution.* The schema's fallback passages (§ Session identity fallback order,
   § Per-session model "Readers", § Model-side resume backstop step 4) let a reader fall back to
   the rollup or the freshest session file and proceed. For this skill that fallback is
   orientation-only (see `--resume`) until the schema is aligned.

**Session identity.** Resolve this session's own stable opaque ID from the host session-I/O
adapter. The schema doc's § Session identity names the Claude source; Codex and GPT have no
bound task-state source, so on those hosts the rule below alone decides which ID qualifies.
Never fabricate, guess, or borrow an ID: not from the freshest session file, not from the
rollup, not from an identity inherited from a launching or parent process's environment (a
coordinator's `CODEX_THREAD_ID` seen by a worker it launched is the coordinator's, not the
worker's), and not from another host's session variable (Codex never reads
`COPILOT_AGENT_SESSION_ID`). An ID that cannot be shown to belong to this executing session is
unavailable. Without it, `--loop` and `--next-task` fail the preflight and `--resume` uses its
orientation-only fallback.

**Preflight (before any `--loop` or `--next-task` write).** Check in order; on the first
failure write nothing and return `Checkpoint not written: required_tool_missing (<item>).`
1. a Git root resolves (`git root`);
2. the schema doc resolves and is readable (`schema`);
3. PowerShell is available and the derive helper resolves and is dot-sourceable
   (`rollup helper`);
4. this session's ID resolves under the identity rule above (`session identity`).
Items 1-3 use § Library resolution: an empty `root` fails item 1; an empty `lib` fails item 2
when no base on the walk held the schema doc (`schema seen: False`), otherwise item 3. A passed
install or build is not evidence that any of these holds now; check at the write.

**Library resolution.** The schema doc named above and the
derive helper (`.claude/hooks/lib/task-state-derive.ps1`) are workspace library files. A
project repository nested inside the coding root (for example `dev/<project>`) usually carries
neither, yet its task state lives in its own Git root (the schema doc's § Multi-level
projects). Both files come from one base, the library base: `$root` if it holds both;
otherwise the enclosing Git root (the `--show-toplevel` of the current base's parent
directory), repeating outward through enclosing Git roots only and stopping when the parent is
not inside a Git work tree. A base that holds only one of the two is passed over, so the schema
doc and the helper never come from different levels. Inside the coding root this reaches the
library the workspace hooks dot-source. The target never moves: session files and the rollup
are always written under `$root/.claude/task-state/`.

Shell variables do not persist across tool calls, so every snippet that needs `$root` or `$lib`
computes them itself in the same PowerShell invocation and never reuses a value from an earlier
call. The snippets target the Windows PowerShell 5.1 floor (no `&&`, `||`, ternary, `??` or
`?.`). The preflight runs this snippet, reads the schema doc under its printed `lib`, and
writes the session file under its printed `root`:

```powershell
$root = git rev-parse --show-toplevel 2>$null
$lib = $root
$schemaSeen = $false
while ($lib) {
    $schemaPath = Join-Path (Join-Path $lib '.claude') 'references/task-state-schema.md'
    $hasSchema = Test-Path -LiteralPath $schemaPath -PathType Leaf
    if ($hasSchema) { $schemaSeen = $true }
    if ($hasSchema -and (Test-Path -LiteralPath "$lib/.claude/hooks/lib/task-state-derive.ps1" -PathType Leaf)) { break }
    $parent = Split-Path -Parent $lib
    $next = if ($parent) { git -C $parent rev-parse --show-toplevel 2>$null } else { $null }
    if ($next -and $next -ne $lib) { $lib = $next } else { $lib = $null }
}
"root: $root"
"lib: $lib"
"schema seen: $schemaSeen"
```

**The rollup is never authority.** `current.md`, and every session file other than this
session's own, is read-only orientation. Never execute its Next Action as this session's, and
never write, close, archive, or release it.

**Locked Next Action bundles.** A `Next Action` that holds a locked
`task-handoff-next-action-v1` bundle is never partially edited, normalized, reformatted or
narrowed. A write that keeps the existing Next Action carries the bundle byte-for-byte; a write
whose caller supplies a new Next Action (a `--next-task` boundary, or build-phase's
`--resume N+1` checkpoint) replaces the whole field under the schema's overwrite rule and never
merges into the bundle. This skill never ingests, validates, previews or executes a bundle;
`--resume` prints it verbatim, adds `Locked bundle held (not executed by task-handoff).`, and
does not run it as a plain command.

None of these modes emits `/compact` or `/clear` — auto-compaction plus, on hosts that have it,
the `SessionStart` re-inject hook handle context in-window (workspace instructions § Session
wrap & commit discipline, loaded through the root CLAUDE.md or AGENTS.md adapter).

## Result lines

`--loop`, `--next-task`, a refused invocation and a failed preflight each end with exactly one
line (`--resume` ends with its orientation block; `--end` ends with session-wrap's output). A
line that begins `Checkpoint written` is success. A line that begins `Checkpoint not written` or
`Checkpoint incomplete` is non-success; the caller's own contract decides what follows
(plan-expedite: its halt template; build-phase and build-step: reported, never a halt class).
This skill never halts its caller by itself.

| Outcome | Line |
|---|---|
| `--loop` written | `Checkpoint written.` |
| `--loop` rollup not regenerated | `Checkpoint incomplete: rollup not regenerated; session file saved.` |
| `--next-task` committed and pushed | `Checkpoint written; committed <short-sha>, pushed <n> commit(s).` |
| `--next-task` with nothing staged | `Checkpoint written; nothing to commit.` — when the branch is ahead of its upstream, add ` (<n> earlier local commit(s) not pushed)` before the period |
| `--next-task` commit failed | `Checkpoint incomplete: commit failed: <reason>; nothing pushed.` |
| `--next-task` push failed | `Checkpoint incomplete: committed <short-sha>, push failed: <reason>.` |
| `--next-task` Git root changed | `Checkpoint incomplete: git root changed after session write; session file saved; nothing staged or pushed.` |
| `--next-task` memory tracking check failed | `Checkpoint incomplete: memory index check failed (git exit <code>); session file saved; nothing staged or pushed.` |
| `--next-task` rollup not regenerated | `Checkpoint incomplete: rollup not regenerated; session file saved; <Git outcome>.` — `<Git outcome>` is the matching row above without its `Checkpoint written; ` or `Checkpoint incomplete: ` prefix and final period (for example `committed <short-sha>, pushed 1 commit(s)`) |
| preflight failure | `Checkpoint not written: required_tool_missing (<item>).` |
| unsupported invocation | `Checkpoint not written: unsupported invocation <arguments>.` |

## `--loop` — checkpoint write

**Cost:** ~5 seconds, no user interaction. Output one line (§ Result lines).

After the preflight, write **this session's own file** — `sessions/<session-id>.md`, where
`<session-id>` is the ID resolved under § Session identity. Read-merge-write *that* file (not
the shared `current.md`), applying the schema doc's per-field append-vs-overwrite rules (it owns
that split). In particular, if the file carries an `**Active project:**` header field (set by
`/user-project`), carry it over **verbatim** — it is a preserve-across-every-write field per the
schema doc; silently dropping it un-pins the session. When the caller keeps the existing Next
Action, carry it over byte-for-byte, including a multiline body. Because the session owns its
file exclusively under a correctly resolved ID, the write never contends with another window.

Then regenerate the derived rollup so `current.md` reflects the freshest session. Run the
block below as ONE PowerShell invocation: it opens with the § Library resolution snippet
verbatim, because no variable survives from the preflight's call, then dot-sources the helper
from the library base and calls it:

```powershell
$root = git rev-parse --show-toplevel 2>$null
$lib = $root
$schemaSeen = $false
while ($lib) {
    $schemaPath = Join-Path (Join-Path $lib '.claude') 'references/task-state-schema.md'
    $hasSchema = Test-Path -LiteralPath $schemaPath -PathType Leaf
    if ($hasSchema) { $schemaSeen = $true }
    if ($hasSchema -and (Test-Path -LiteralPath "$lib/.claude/hooks/lib/task-state-derive.ps1" -PathType Leaf)) { break }
    $parent = Split-Path -Parent $lib
    $next = if ($parent) { git -C $parent rev-parse --show-toplevel 2>$null } else { $null }
    if ($next -and $next -ne $lib) { $lib = $next } else { $lib = $null }
}
"root: $root"
"lib: $lib"
"schema seen: $schemaSeen"
if (-not $root -or -not $lib) {
    'rollup not regenerated'
} else {
    . "$lib/.claude/hooks/lib/task-state-derive.ps1"
    $written = Write-DerivedRollup $root
    if ($written) { "rollup written: $written" } else { 'rollup not regenerated' }
}
```

The helper never throws; it returns the path it wrote, or `$null` when it could not write (a
concurrent rollup writer can cause this even though nothing is lost, because the rollup is
regenerable). After this session's file was written, the block's last line decides. A last
line of `rollup not regenerated` is a rollup failure: `root` or `lib` was empty in this
invocation (then nothing is dot-sourced), or the helper returned `$null` or empty. A printed
`root` that differs from the root whose session file was just written (the working directory
moved between calls) is also a rollup failure. On a rollup failure `--loop` returns its rollup
line, not `Checkpoint written.`, and `--next-task` continues (its step 1). Do not use
`Resolve-ActiveSessionStatePath` in this skill; its own → freshest → rollup order serves hooks
and returns a foreign file without saying so.

`current.md` is a DERIVED rollup (the freshest session wholesale + a listing of the others),
regenerated by the helper — never hand-written, never a write target. **No git commit** —
`sessions/*.md` and `current.md` are gitignored session-local state, so a routine checkpoint
touches no tracked file.

Callers invoke it after each meaningful action — tests pass, a hypothesis is ruled out,
before a new iteration. It should feel nearly zero-cost.

**`--loop --no-commit`** — a backward-compatible no-op alias. It predates gitignored
task-state (when `--loop` committed `current.md` and `build-phase` Step 2e needed the commit
suppressed). Now that a routine `--loop` commits nothing, `--no-commit` and `--loop` are
identical; `build-phase` may keep passing it.

## `--next-task [label]` — task-boundary save

**Cost:** ~30 seconds. Durable boundary write when switching tasks within the same goal
(e.g. plan-expedite → build-phase), in this order:

1. Preflight, then the same session-file read-merge-write and rollup regeneration as `--loop`.
   The finished task's entries land in Completed (append); WIP, Next Action, and Status are
   overwritten to point at the next task (`[label]`); a held locked bundle is replaced whole
   (§ Locked Next Action bundles). On a preflight failure, stop with that line. A rollup
   failure does not stop the boundary — the session file is saved and the rollup is
   regenerable — so continue and report it in step 6.
2. Update the host memory index (`MEMORY.md`) on disk.
3. Before any Git mutation, re-resolve the Git root from the directory where the add would run
   and compare it with the root printed by step 1. If either root is empty or they differ after
   path normalization, stage and push nothing and return the Git-root-changed result line. This
   prevents a moved working directory from publishing another repository's changes.
4. Scoped add (`git add <paths>`; never `git add -A` — the workspace carries parallel-session
   churn): the code paths this session changed, plus `MEMORY.md` only when it is already
   tracked in this Git root. Decide that by running the block below as ONE PowerShell
   invocation from the directory the add runs in. Replace `<session-root>` with the root printed
   by step 1; the block resolves its own current root because no variable survives from step 1:

   ```powershell
   $sessionRoot = [IO.Path]::GetFullPath('<session-root>').TrimEnd('\')
   $root = git rev-parse --show-toplevel 2>$null
   if (-not $root -or [IO.Path]::GetFullPath($root).TrimEnd('\') -ne $sessionRoot) {
       'git root changed after session write; nothing staged'
   } else {
       $null = git -C "$root" ls-files --error-unmatch -- MEMORY.md 2>$null
       $memoryExit = $LASTEXITCODE
       if ($memoryExit -eq 0) {
           "memory index: tracked; stage $root/MEMORY.md"
       } elseif ($memoryExit -eq 1) {
           "memory index: not tracked in $root (git exit 1); not staged"
       } else {
           "memory index check failed in $root (git exit $memoryExit); nothing staged"
       }
   }
   ```

   Its last line decides and stays in the output. A root-changed or memory-check-failed line
   stops before every add and returns its matching incomplete result. Otherwise stage the
   printed `<root>/MEMORY.md` only when the line begins `memory index: tracked;`. Exit 1 means
   the file is not tracked; every other non-zero exit is a failed check, never silently treated
   as an untracked file. A memory index outside the root (for example Claude's per-project
   memory directory), or an untracked one inside it, is updated on disk and never staged.
   Never stage the gitignored task-state.
5. If the add staged nothing, skip the commit and do not push.
6. Otherwise commit, then push. The push sends the branch tip, so it also publishes any earlier
   unpushed local commits beneath it; the result line reports how many commits were pushed.
7. Return the matching line (§ Result lines); after a rollup failure in step 1, use the
   `--next-task` rollup row.

Then **keep working in-window**. No manual `/compact` is needed to cross a task boundary.
If a *deliberate* focused reset is genuinely wanted (not the default), emit a
`/compact [focus]` line for the user to type — `/compact` has no programmatic trigger.

## `--resume` — in-window orient

Reads **this session's own** `sessions/<session-id>.md` plus git state, and outputs an
orientation block — no window switch. Use after a compaction. After `/clear` it finds this
session's file only if the host keeps the same session ID across `/clear`; otherwise the
orientation-only fallback below applies. Reading your own session file (not the shared rollup)
means a concurrent window's checkpoint can never surface as *your* Next Action.

```
Resuming [Task field]: [Status]
[Next Action field verbatim]
```

If the file is not stale, proceed with the next action — do NOT ask for confirmation (a locked
bundle is held, not run; see § Locked Next Action bundles). It is stale when `Last written` is
more than 8 hours before UTC now (the schema doc's § Staleness threshold); an unparseable
timestamp is unknown age, not stale — never fabricate an age. If it is stale, follow the block
with the schema's stale banner
`state is <N> hours old -- verify against git before trusting Next Action` and do not execute
the Next Action.

**Orientation-only fallback.** If no stable ID is available, or this session has no file yet
(a fresh window), read the derived `current.md` rollup, then the freshest session file, for
orientation only (resolve these paths directly in that order):

```
No active task state found for this session — orientation only.
Freshest recorded session: [Task field]: [Status]
Its Next Action (not executed): [Next Action field verbatim]
```

Execute nothing from it and write nothing; the caller's next command or the operator chooses
the work. If no rollup or session file exists, output `No active task state found — starting
fresh.`

## `--end` — true session end

Invokes `/session-wrap --end` through the host's skill-invocation adapter; session-wrap owns
the end-window route, including its Git verb (scoped commit and push, or `/repo-update`).
