# Capability-aware build routing and blocked-goal handling

Status: implementation of the scoped routing repair was authorized on 2026-11-01; see
[repair scope and evidence](../../documentation/capability-aware-routing-repair.md).
The original seed granted no implementation, installation, gate waiver or catalog authority.
Captured: 2026-10-31.

## Problem and operator outcome

The operator should receive an executable route for their intended work, with its
constraints checked before a preparation chain or unattended goal is recommended.
A pipeline failure must not become repetitive status-only goal continuations or a
reason to imply that useful implementation has occurred.

The observed incident was in the sibling you-asked-for-it project. A bounded,
evidence-driven animation/combat experiment was prepared through plan-expedite,
including proposal and issue sync, then recommended as an eight-hour build-phase
goal. The plan explicitly prohibited staging, commits and pushes and preserved a
large dirty checkout. Build-phase normally uses worktrees and checkpoint commits.
These execution differences were mentioned but not resolved before recommending
that route. No claim is made that those git differences caused the observed halt.

## Observed evidence versus uncertainty

- Goal start: 2026-10-31 22:59:22 UTC; hard stop: 2026-11-01 06:59:22 UTC.
- Installed Codex build-phase required a fresh-agent acceptance probe before any
  code step. A disposable verdict service started with the expected schema.
- Fresh child dispatch returned exactly: `collab spawn failed: agent thread limit reached`.
- Existing completed children remained listed. No close/release-agent capability
  was exposed. Thread capacity is not interchangeable with active concurrency.
- The parent closed the disposable service successfully. No candidate channel,
  implementation step or gameplay test ran. No files were staged or committed.
- Two automatic goal continuations restated the same blocker before goal status
  was marked blocked on the third consecutive goal turn, following the host's
  blocked-audit threshold. These continuations produced no product progress.
- The caller-scoped handle, conversation challenge and later signing checks were
  NOT completed. The incident proves dispatch exhaustion, not failure of those
  isolation properties. A fresh conversation might restore capacity; it does not
  prove the rest of the pipeline is supported.
- Local evidence remains in the sibling project's named preparation and blocked
  build handoffs; do not copy private session/intent records into this public repo.

## Candidate repair scope

1. **Check route compatibility before recommending it.** user-build-route and
   plan-expedite's continuation should consider the selected installed provider,
   concrete required capabilities, current capacity when observable, dirty-tree
   semantics, publication constraints and testing budget. Distinguish prepared
   plan, eligible execution route, and freshly qualified runtime capability.
   Preparation can succeed while execution remains unqualified; say so clearly.
2. **Keep checks proportional.** Read-only capability/constraint inspection first;
   avoid running a full costly probe just to answer routing advice. Label unknowns.
   Revalidate volatile capacity at dispatch; do not treat old qualification as a
   permanent certificate. Do not consume the last usable agent slots proving a
   route without a lifecycle/capacity strategy for the actual work.
3. **Offer the smallest supported route without weakening gates.** A bounded
   art experiment with no-git-mutation constraints may belong on a direct goal
   with independent review. Never silently turn build-phase into direct execution,
   self-review, a legacy adapter or a supposedly authenticated PASS. Changing
   route must preserve the user's contract and any required approval boundary.
4. **Separate capability failure from project failure.** Persist one compact
   structured blocker: stage, exact observed error, unfinished checks, completed
   work, deadlines, cleanup and the external change needed. No fake step-start,
   DONE status, passing review or readiness claim.
5. **Handle goal re-drive without noise.** Respect the host's blocked-audit
   threshold; do not mark blocked prematurely or complete an unfinished goal.
   Before the threshold, use cheap state revalidation and continue genuinely
   independent authorized work where the chosen contract permits it. Do not
   repeat unchanged failed probes, duplicate issues or handoffs, or keep issuing
   user-facing status restatements. At threshold, mark blocked once. A resumed
   goal starts the host-defined fresh audit, not an invented exception.
6. **Make recovery honest.** Supply one pasteable continuation that names the
   remaining work, original deadline and review obligations. Restarting a chat
   must not silently restart the clock. An explicitly requested new time window
   is a new authorization, recorded as such.

## Bounded first milestone

Reproduce route selection on three recorded scenarios: exhausted fresh-agent
capacity, a dirty/no-commit experiment, and a supported ordinary build. Propose
one routing/continuation correction with the smallest necessary source changes.
Avoid a new scheduler, agent manager, capability registry or general framework.
Any catalog change follows documentation/skill-catalog-lifecycle.md; never edit
installed generated profiles as the repair.

## Definition of done for a future implementation

- Evidence distinguishes known support, unknown capability and observed failure.
- The no-commit/dirty experiment gets a compatible recommendation or an explicit
  incompatibility before an unconditional build continuation is issued.
- Failed required probes remain fail-closed; no prose or reused reviewer grants PASS.
- Capacity tests use the actual supported host seam; mocks alone do not qualify it.
- A re-drive scenario respects the three-turn host rule without duplicate external
  mutations, repeated probes or a misleading stream of progress messages.
- Recovery preserves deadline, original scope, independent review and acceptance.
- A positive supported-build case still executes normally; no blanket ban on pipelines.
- Focused regression checks, applicable release checks and independent review are
  recorded honestly. An actual consumed-host observation verifies the final route.

## Non-goals

Fixing the game's artwork in Skill Mesh; removing isolation/signing safeguards;
claiming all hosts support the same tools; resetting budgets automatically;
creating an alternative pipeline inside a project adapter; mass catalog refactors.
