why this shape

The rails exist; the unknown is fenced.

skill-mesh is already a two-provider, manifest-driven system — 50 skills, deterministic generation, transactional install with ledger-scoped uninstall. Codex is a third provider on proven rails, not a new architecture. The one genuine unknown — whether Codex actually discovers skills at .agents/skills — is unproven on this machine, so the plan authors only 5 providers before testing it live (M1), and cohorts B–D are conditional on M1: PASS. Worst case on failure: one authoring step sunk, not forty-seven.

what could bite

And the built-in answer.

  • Codex doesn't read .agents/skills → M1 fires after only 5 providers exist; cohorts stay skipped; sunk cost ≈ one step.
  • Skill-list budget truncation (8,000-char floor, 47–54 names) → budget tests from Step 3; M1/M2 verify on the real host; descriptions are authored and trimmable.
  • Step-4 failing test is a real installer defect → Step 2 demands root-cause fix + full suites before anything builds on the installer.
  • Heavy skills degrade on Codex (no Agent/Workflow/Artifact) → cores already define fallbacks + required_tool_missing halts; degradations become delta rows, never silent.
  • plan.md hygiene tests assert exact strings → impact table pins them (Provider expansion | PARKED survives Step 1's edit); full-root gate proves it.
