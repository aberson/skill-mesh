Disposable driver-test environment

A provider-neutral, fail-closed plan for moving driver, App Control, boot, and genuine-host evidence off the real workstation into one disposable Windows execution guest, while keeping the private test publisher in a separate isolated signer appliance.

Planning reviewed; execution not authorized
What I heard Why this shape Timeline Afterwards Operator choices Agent defaults Not in v1 Risks Feedback

What I heard

Plan a dedicated disposable environment for C2N through C4. Do not change this workstation's certificates, Code Integrity/App Control policies, Secure Boot, or boot configuration.

C2V and C2A are already sealed. A read-only prerequisite check showed this workstation does not have the qualifying WDK, signing identity, or enforced admission policy needed by C2N. The safe response is a separate test target—not remediation of the real machine.

Why this shape

Execution and signing are separated

C2N discovery, C3 native/security work, and C4 attended acceptance stay on one S1/R0 execution lineage. A separate non-snapshotted appliance holds the private publisher key and never runs candidate code.

Parent keeps authority

The coordinator alone owns provider leases, asymmetric admin/signing grants, Git integration, review classification, and final verdicts. Only independently reviewed exact objects can reach the signer appliance. A producer can never certify its own output.

Failure has an owner

After Step-4 selection, while both the environment ID and every provider resource are absent, an authenticated closure destroys every committed key, journal, store, and provider authorization and proves every never-committed planned allocation absent. Once an environment ID or provider resource exists, every terminal C2E/C2N/C2P/C3/C4 branch runs disposition. Abort cleanup cannot unlock C5; a failed C4-PASS retention transition immediately destroys the whole lineage and records a blocker.

Hard boundary: no local hypervisor install, certificate import, App Control/Code Integrity change, Secure Boot change, BCD change, WDK install, driver action, or genuine host session is authorized by this proposal.

Operator-picked choices

P1

Dedicated disposable C2N–C4 environment

This is the approved planning objective.

P2

No workstation security/boot mutation

Certificates, Code Integrity policies, Secure Boot, and boot configuration are outside the authorized surface.

Not yet picked: provider, image/license, cost ceiling, private artifact service, external publication broker, and retention owner. A separate execution authorization is required before Step 1; C2E.4 then stops for those provider decisions, and C2E.29 stops again before provisioning.

Agent defaults

D1

One execution guest plus one signer appliance

Keeps native build/policy/driver behavior on one measured S1/R0 lineage while moving the private signing key outside the untrusted-kernel boundary.

A different topology needs equivalent toolchain, key-isolation, and no-route proof.

D2

Provider-neutral contract, selected concrete adapter

Repository semantics stay portable while runtime integration is real and testable.

Choose the provider at C2E.4; no provider is assumed here.

D3

Coordinator owns authority

Separates production, review, admin, Git, and final-verdict powers.

Authority can move only with an equivalent authenticated boundary.

D4

Canonical closed 16-operation connector

RFC 8785-plus-LF bytes, separate authority planes, domain-separated length-delimited full-envelope proofs, an immutable locator-free bootstrap, and transactional control/resource/guest replay journals close arbitrary shell, path, wildcard, implicit resource, stale-state, orphan, and crash-retry escapes.

A provider adapter may translate mechanics, not widen the operation, canonical-byte, proof, authority, tagging, or journal sets.

D5

Public-only S1/R0 and one writable descendant

Separates reusable tools from run-specific public trust, keeps the private leaf out of snapshots, and prevents simultaneous divergent runs.

A different topology needs equivalent lineage, key isolation, and exclusivity proof.

D6

Guest-only test trust posture

Secure Boot off plus TESTSIGNING is the ordinary disposable driver-test route; HVCI remains on; App Control enforces one exact Publisher-level PCA-TBS-plus-leaf-CN rule in both user and kernel scenarios.

Use another Microsoft-supported route only after re-planning its boot/signing contract.

D7

One common-parent encrypted run volume

Matches the frozen UAT exactly. The retained disk is private because deleted roots can leave block remnants.

Topology cannot change without authoritative UAT/plan action.

D8

Observed 28000.2804 baseline, rechecked at execution

Avoids stale PATH selection and records dated supported servicing facts.

C2E.4 may record newer official versions before provisioning.

D9

Thirty-three bounded steps

Keeps each code atom and authority plane reviewable, makes provider/human boundaries machine-stopping, and keeps build-phase away from push/seal/disposition waits.

Steps may be split further; Steps 4, 29, 30, 32, and 33 may not be collapsed into build-phase.

D10

C2E inventories; C2N selects

Preserves the existing stage owner and prevents readiness from pre-selecting tool inputs.

None without changing the authoritative completion contract.

D11

Automatic retention expiry

A calendar note is not cleanup. Only a remotely proven C4 PASS may atomically destroy runnable state and reclassify the detached run volume to a fixed C4-plus-120-day rule; a separate verifier later proves absence.

Failure quarantine is fixed at the earlier of the immutable stop receipt plus seven days or the original 30-day deadline; C5 uses signed authorization plus 90 days. No caller may reset or extend those bounds.

D12

Active provider authority revoked last

Cleanup needs control-plane authority through power-off, inventory, destruction/quarantine, lease release, and receipt verification.

Successful PASS retention also preserves read-only verification, credential-free C5 preauthorization, and control/wait/emergency proof authorities only through C5 teardown; every other route removes them.

D13

Exactly authenticated wait results

A provider success string or producer assertion cannot advance execution. The parent uses the fixed RSA/SPKI/PSS profile, binds the selected adapter, and requires the API-returned marker ID to equal the exact remote reread before committing facts.

Storage can vary; key profile, parent-only signing, exact enums, selector tuple, and ordering cannot.

D14

Root pytest DONE gates

Package-integrity is fast feedback, not repository-wide certification.

Gate frequency may be revisited only if project instructions change.

D15

Separate asymmetric admin grants

The guest connector HMAC proves session membership, not parent authorship. A non-self-referential payload hash and domain-separated exact signature let only the distinct parent key authorize one elevated action.

Key implementation can vary; canonical proof scope and the ban on HMAC-granted elevation cannot.

D16

Isolated RSA-3072/SHA-256 chain

The root, PCA, and signing leaf use one closed X.509 v3 profile with bounded validity and one no-timestamp SHA-256 Authenticode signature, while the signer appliance has no execution-guest route, runs no candidate code, and accepts one independently reviewed exact object under one parent grant.

Equivalent isolation is acceptable only with the same whole-chain profile, no-route, source/object-review, positive, and denial proofs.

D17

Separate control and guest receipts

A powered-off or destroyed guest cannot attest its own control state. Provider-control results need independent reread and parent signature.

Provider mechanics can vary; the authority split and tagged schema cannot.

D18

Active expiry and direct emergency cleanup

A lost coordinator must not leave privileged resources indefinitely. Provider rules enforce 30-minute lease, five-minute power-off, 60-minute descendant destruction, 30-day complete-lineage destruction, and 60-day control/wait/broker/C5-preauthorization maxima.

C2E.4 may shorten active-lifecycle maxima. Emergency safety cannot depend on Git, tests, build-phase, GitHub, or control/wait signers.

D19

Kernel entry makes the descendant untrusted

A candidate kernel image can control guest-local events, HMAC, services, and files. Security claims therefore depend on pre-sign source/object review and external provider/signer facts, not guest self-attestation.

If a required claim cannot be externally corroborated or accepted as attended behavior of the reviewed bytes, stop.

D20

Failed PASS retention becomes destroy-only

A C4 PASS does not justify leaving an ambiguously retained or partially transitioned volume. If the atomic transition cannot be verified, the broker destroys the whole lineage and preserves both the PASS and transition failure.

This route records C2E.33 BLOCKED and never makes C5 eligible.

D21

C5 gets one exact signed intent and identity

The active provider identity is intentionally gone after C2E.33. A remotely reread pending candidate and domain-separated parent-signed intent unlock one new one-hour shortener; no reusable credential survives from the active run.

Revoke the shortener and preauthorization after use, then destroy control/wait/emergency authorities before final DONE.

D22

Wait key is the first allocation

Every partial provider-selection failure must still have a valid authenticated cleanup path.

The first atomic allocation is reconciled and sign-tested; closure binds either the private selection attempt or the final PASS.

D23

Private profile-signed toolchain manifest

Emergency build atoms need exact tools, libraries, arguments, identities, ACL facts, and a domain-separated signature without leaking host paths or handles into Git or child prompts.

Only the parent receives a process-scoped opaque retrieval handle and verifies the content-addressed manifest.

D24

Read and transfer are separate atoms

Read-only dispatch and content-addressed transfer are independently observable connector behaviors.

Each gets its own implementation, tests, review, and dependency edge.

D25

GitHub credential stays external

A candidate kernel can read guest process memory. Each upload therefore receives only a separate five-minute capability bound to issue 153, one exact body and ordinal; the broker keeps the real credential.

Direct GitHub API egress is denied, and wrong-body, replay, third-use, expiry, and reuse attempts must fail.

Not in this planning deliverable

  • No provider purchase or selection, VM creation, image download, software installation, or host restart.
  • No certificate, App Control/Code Integrity, Secure Boot, BCD, firmware, WDK, service, or driver change on this workstation.
  • No C2N discovery, C2P plan, Step-108P containment implementation, C3 certification, or C4 host session.
  • No edit to the accepted Phase IS plan or frozen UAT.
  • No production signing, HLK certification, Partner Center submission, or non-disposable deployment.
